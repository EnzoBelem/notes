# TOML e pyproject.toml

#Python

## O que é TOML

TOML significa **Tom's Obvious, Minimal Language**. É um formato de arquivo de configuração criado em 2013 por Tom Preston-Werner, cofundador do GitHub, que também criou o Jekyll e o Gravatar. A motivação era ter algo:

- mais legível para humanos do que **JSON**: sem vírgulas, chaves e aspas obrigatórias, e com suporte a comentários;
- menos traiçoeiro do que **YAML**: a indentação sensível e as regras implícitas geram surpresas, como o famoso "problema da Noruega", em que `NO` (código do país) vira o booleano `false` no YAML 1.1.

A versão 1.0 da especificação saiu em janeiro de 2021, estabilizando a linguagem.

### Sintaxe básica

```toml
# Comentários começam com #
titulo = "Exemplo"             # string
porta = 8080                   # inteiro
pi = 3.14                      # float
ativo = true                   # booleano (minúsculo)
criado_em = 2024-05-01T10:30:00-03:00   # data/hora é um tipo nativo
linguagens = ["python", "rust"]         # lista

[servidor]                     # tabela (seção)
host = "127.0.0.1"

[servidor.tls]                 # tabela aninhada: servidor.tls
ativo = false

[[usuarios]]                   # array de tabelas: cada [[usuarios]] adiciona um item
nome = "ana"

[[usuarios]]
nome = "bia"

ponto = { x = 1, y = 2 }       # tabela inline (em uma linha só)
```

Os tipos são explícitos: `"8080"` é string e `8080` é inteiro. Não há conversão implícita.

## Contexto: como pacotes Python funcionam

Em resumo, um pacote Python nada mais é que um diretório com código que podemos baixar e acoplar aos nossos projetos.

**Fluxo de uso de pacotes**

- Pacotes estão diretamente ligados ao uso de **ambientes virtuais**.
- O **PyPI** é o índice público de pacotes Python.
- O **pip** faz o link entre o PyPI e os ambientes virtuais.
- No fim, o uso do pip costuma se resumir a um arquivo `requirements.txt` com as dependências do projeto.

**Fluxo de criação de pacotes**

- Usa-se a biblioteca **build** e o arquivo `setup.py`, que diz como instalar o projeto e carrega muitos outros metadados para gerar o pacote.
- Todo esse fluxo está atrelado ao **setuptools**, mantido pela **PyPA** (*Python Packaging Authority*, o grupo que mantém as ferramentas e os padrões de empacotamento).

É esse segundo fluxo, o de criação, que o `pyproject.toml` veio padronizar.

## O problema que o `pyproject.toml` resolveu

Por muito tempo, empacotar Python significava ter um `setup.py`, que é **código executável**. Para saber os metadados ou as dependências de um projeto, era preciso rodar o script. Isso é inseguro, difícil de analisar por ferramentas e cheio de armadilhas.

Além disso:

- o `setup.py` assumia que você usava o setuptools, e não havia forma padrão de dizer "construa meu projeto com outra ferramenta";
- o pip precisava do setuptools para ler o `setup.py`, mas não tinha como saber se ele estava instalado (o problema do ovo e da galinha);
- cada ferramenta de lint, formatação e teste espalhava sua configuração em arquivos próprios (`setup.cfg`, `tox.ini`, `.flake8`, `.coveragerc`).

## Linha do tempo

| Ano | Marco | O que mudou |
| --- | --- | --- |
| 2013 | TOML criado | Formato de configuração legível. Já era usado pelo `Cargo.toml` do Rust. |
| 2016 | **PEP 518** | Cria o `pyproject.toml` com a tabela `[build-system]`, que declara os **requisitos de build** do projeto. O espaço `[tool.<nome>]` fica reservado para configuração de ferramentas. O pip só passou a respeitá-la na versão 10 (2018). |
| 2017 | **PEP 517** | Define uma interface padrão para *backends de build*. Qualquer ferramenta (flit, poetry-core, hatchling, setuptools) pode ser declarada em `[build-system]` e o pip a invoca de forma uniforme. O pip passou a suportar a PEP 517 na versão 19.0 (2019). |
| 2018 | **Poetry** e **Black** | O Poetry usa o `pyproject.toml` como arquivo central de dependências e metadados. O Black adota `[tool.black]` e abre o precedente de ferramentas guardarem sua configuração ali. Depois vieram pytest, mypy, isort, coverage, ruff e outras. |
| 2020 | **PEP 621** | Define a tabela `[project]` com campos padronizados (nome, versão, dependências, autores, licença...), independentes de ferramenta. Antes, cada backend tinha seu jeito de declarar metadados. O setuptools passou a ler `[project]` na versão 61 (2022). |
| 2022 | **Python 3.11** | A biblioteca `tomllib` entra na stdlib, somente para leitura. É o reconhecimento oficial do formato. |
| 2024 | **PEP 723** e **PEP 735** | A PEP 723 permite declarar dependências de um script avulso em um bloco TOML dentro de comentários. A PEP 735 cria os *dependency groups* (`[dependency-groups]`), que expressam dependências de desenvolvimento sem fazer parte do pacote publicado. |

> O **flit** já usava o `pyproject.toml` antes mesmo da PEP 518 ser finalizada, mas foi o Poetry que mostrou, na prática, que a experiência era boa.

### Por que TOML e não YAML ou JSON?

A escolha foi deliberada e discutida na PEP 518:

- JSON não tem comentários e é desconfortável de editar à mão.
- YAML é complexo demais, e exigiria um parser pesado como dependência do próprio bootstrap do empacotamento.
- TOML já tinha boa reputação de legibilidade e era simples o bastante para ter parsers pequenos e consistentes.

## As três tabelas do `pyproject.toml`

```toml
[build-system]                    # PEP 518/517: COMO construir o projeto
requires = ["hatchling"]
build-backend = "hatchling.build"

[project]                         # PEP 621: O QUE é o projeto
name = "meu-projeto"
version = "1.0.0"
description = "Uma descrição curta"
readme = "README.md"
requires-python = ">=3.9"
license = { text = "MIT" }
authors = [{ name = "Fulano", email = "fulano@exemplo.com" }]
dependencies = [
    "django>=4.2",
    "djangorestframework",
]

[project.optional-dependencies]   # extras: pip install "meu-projeto[docs]"
docs = ["mkdocs"]

[project.scripts]                 # cria o comando `meu-cli` no PATH
meu-cli = "meu_projeto.cli:main"

[dependency-groups]               # PEP 735: dependências de desenvolvimento
dev = ["pytest", "ruff"]

[tool.ruff]                       # [tool.<nome>]: configuração de ferramentas
line-length = 100

[tool.pytest.ini_options]
testpaths = ["tests"]
```

| Tabela | Obrigatória? | Quem lê |
| --- | --- | --- |
| `[build-system]` | Não, mas é fortemente recomendada. Sem ela o pip assume setuptools legado. | pip e os backends de build |
| `[project]` | Não. Pode ser omitida se o projeto não vai ser empacotado. | pip, backends e ferramentas de gestão (uv, poetry, hatch) |
| `[tool.*]` | Não | Cada ferramenta lê só a sua própria tabela |

## O que o arquivo substituiu

| Antes | Agora |
| --- | --- |
| `setup.py` (código) | `[project]` + `[build-system]` |
| `setup.cfg` | `[project]` e `[tool.setuptools]` |
| `.flake8`, `.coveragerc`, `tox.ini`, `mypy.ini` | `[tool.ruff]`, `[tool.coverage]`, `[tool.mypy]`... |
| `requirements-dev.txt` | `[dependency-groups]` ou `[project.optional-dependencies]` |

O `requirements.txt` não desaparece: ele continua útil para **travar versões exatas** (lockfile) em uma aplicação. O `pyproject.toml` declara o que o projeto *aceita*, e o lockfile registra o que foi *instalado*. Ferramentas como `poetry` (`poetry.lock`) e `uv` (`uv.lock`) geram esse lockfile automaticamente.

## Lendo um arquivo TOML em Python

```python
import tomllib  # Python 3.11+

with open("pyproject.toml", "rb") as f:   # atenção: modo binário
    dados = tomllib.load(f)

print(dados["project"]["name"])
```

- O `tomllib` só **lê**. Para escrever TOML, use uma biblioteca como `tomli-w`.
- Em versões anteriores ao 3.11, instale `tomli` (é o código que virou `tomllib`): `pip install tomli`.

## Por que o formato "venceu"

- **Segurança e previsibilidade:** é dado declarativo, não código, então as ferramentas leem sem executar nada.
- **Neutralidade:** o padrão descreve *como declarar*, não qual ferramenta usar.
- **Consolidação:** um arquivo no lugar de `setup.py`, `setup.cfg`, `requirements.txt` parcial, `tox.ini` e configs soltas.
- **Legibilidade:** comentários, tipos explícitos e sem pegadinhas de indentação.

## Hoje

O `pyproject.toml` é o ponto central de um projeto Python moderno. Ferramentas como **uv**, **Hatch** e **PDM** nascem em torno dele, e o Rye (que hoje aponta o uv como sucessor) seguia o mesmo caminho. O Poetry usa `[tool.poetry]` desde o início e passou a aceitar o `[project]` padrão na versão 2.0 (2025). O `setup.py` ficou como legado. A especificação oficial do arquivo é mantida pela PyPA em packaging.python.org.

## Migração de projetos legados

Para projetos antigos, inclusive os que ainda rodam em Python 3.6, dá para migrar aos poucos:

1. Crie um `pyproject.toml` apenas com `[build-system]` (por exemplo, `requires = ["setuptools"]` e `build-backend = "setuptools.build_meta"`). O pip a partir da versão 10 já o respeita.
2. Mova a configuração das ferramentas (`black`, `isort`, `pytest`...) para `[tool.*]`.
3. Quando o setuptools for 61 ou superior, mova os metadados do `setup.py`/`setup.cfg` para `[project]` e então remova o `setup.py`.

Isso não exige trocar a versão do interpretador, mas as versões do pip e do setuptools que sustentam cada passo podem pedir um upgrade deles.
