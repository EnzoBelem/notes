# Como o uv funciona

#Python

Esta nota explica como o [[4.6. uv]] opera por baixo dos panos, principalmente em comparação com o `pyenv` e o `pip`.

## 1. Sem shims: invocação direta de binários

O `pyenv` funciona interceptando comandos por meio de **shims**: scripts *wrapper* colocados no início do `$PATH` que descobrem qual versão do Python deve ser usada e só então delegam a execução. Isso adiciona uma pequena camada de overhead a cada chamada.

O uv **não usa shims**:

- **Downloads standalone:** ele baixa distribuições de Python pré-compiladas (os builds *python-build-standalone*) para um diretório próprio de Pythons gerenciados. Esse diretório **não é o cache**: `uv cache clean` não apaga os Pythons instalados. Para ver o local, use `uv python dir`.
- **Execução direta:** ao rodar `uv run` ou `uv venv`, o uv localiza o executável exato da versão pedida (via `--python`, via `.python-version` ou via o `requires-python` do `pyproject.toml`) e o invoca diretamente.
- **Sem ativação manual:** o `uv run` ajusta as variáveis de ambiente necessárias para o processo rodar dentro do `.venv` correto, dispensando o `source .venv/bin/activate`.
- **Descoberta de interpretadores:** o uv considera primeiro os Pythons que ele mesmo gerencia e também os que encontra no sistema (`PATH`). Para forçar um dos dois, use `--managed-python` (só Pythons gerenciados pelo uv) ou `--no-managed-python` (só os do sistema), ou as variáveis `UV_MANAGED_PYTHON` e `UV_NO_MANAGED_PYTHON`.

Por não compilar nada na sua máquina, a instalação é de segundos, ao contrário do `pyenv install`, que compila o CPython a partir do código-fonte.

## 2. Cache global e vinculação de arquivos

No `pip` tradicional, cada ambiente virtual guarda uma **cópia independente** de todas as dependências.

O uv usa um **cache global centralizado**:

- Quando um pacote (*wheel*) é baixado do PyPI, ele é descompactado e guardado no cache global (`uv cache dir`; no Linux, normalmente `~/.cache/uv`).
- Ao instalar a dependência em um projeto, o uv **vincula** os arquivos do cache ao `.venv` por *hard links* (ou por *clones* copy-on-write, nos sistemas de arquivos que suportam).
- Assim, pacotes são reutilizados entre vários projetos quase instantaneamente, e o uso de disco cai bastante, porque os arquivos existem uma só vez.

Os modos de vinculação (`UV_LINK_MODE` ou `--link-mode`) são `clone`, `hardlink`, `copy` e `symlink`. O padrão é `clone` no macOS e `hardlink` no Linux e no Windows.

> **Atenção:** *hard links* só funcionam dentro do **mesmo sistema de arquivos**. Se o cache (`~/.cache/uv`) e o projeto estiverem em partições diferentes, por exemplo um projeto em `/mnt/data` e o cache na `home`, o uv avisa que não conseguiu criar os links e cai para **cópia**, que é mais lenta e usa mais disco. Para silenciar o aviso, defina `UV_LINK_MODE=copy`. Para manter os links, aponte o cache para o mesmo disco do projeto com `UV_CACHE_DIR`.

Cuidados com os hard links: como os arquivos são compartilhados, modificar manualmente um arquivo dentro do `site-packages` pode afetar outros ambientes que usam o mesmo pacote.

## 3. Motor de resolução e desempenho em Rust

- **Rust:** o uv é compilado para código nativo, com alto paralelismo nas operações de rede (downloads) e de disco, e sem o custo de iniciar um interpretador Python.
- **Resolvedor próprio:** o uv traz um resolvedor de dependências integrado (baseado no algoritmo PubGrub), que resolve grafos de dependências complexos com rapidez e mensagens de erro mais claras quando há conflito.
- **Lockfile universal:** o `uv.lock` registra a resolução para **todas as plataformas e versões de Python** suportadas pelo projeto, e não só para a máquina em que foi gerado. Isso permite versionar um único arquivo e obter o mesmo resultado no Linux, no macOS e no Windows. O arquivo é TOML (veja [[4.5. TOML e pyproject.toml]]).
- O ganho de velocidade informado pelo projeto é de 10 a 100 vezes em relação ao `pip`. O ganho depende do cenário: ele é maior com cache aquecido, e menor quando o tempo é dominado pelo download de pacotes grandes.

## 4. Ambientes efêmeros para ferramentas e scripts

- **Ferramentas CLI (`uvx` / `uv tool run`):** ao rodar um utilitário como `uvx pycowsay`, o uv monta um ambiente virtual temporário a partir do cache, executa o binário do pacote e o descarta. Como os arquivos vêm do cache global (veja a seção 2), isso leva uma fração de segundo.
- **Ferramentas instaladas (`uv tool install`):** cada uma ganha seu ambiente virtual próprio e persistente, e só os executáveis são expostos no `PATH`. É a mesma ideia do [[4.1 pipx]].
- **Scripts individuais (`uv run script.py`):** o uv lê o bloco de metadados inline (PEP 723) do arquivo e prepara um ambiente isolado só para aquela execução.

## Resumo das diferenças

| Aspecto | `pyenv` + `pip` + `virtualenv` | `uv` |
| --- | --- | --- |
| Instalar uma versão do Python | Compila a partir do código-fonte | Baixa um binário pré-compilado |
| Seleção da versão | Shims no `PATH` | Invocação direta do binário |
| Dependências entre projetos | Uma cópia por ambiente | Cache global com *hard links* |
| Ativar o ambiente | `source .venv/bin/activate` | `uv run` (não precisa) |
| Lockfile | `requirements.txt` por plataforma (via `pip-tools`) | `uv.lock` universal |
| Linguagem | Python | Rust |
